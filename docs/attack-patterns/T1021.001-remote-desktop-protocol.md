# T1021.001 - Remote Desktop Protocol

## The Attack - What Actually Happens
Volexity's 2024 "Nearest Neighbor Attack" report documents an unusually
concrete example: APT28 (GruesomeLarch) compromised a system at one
organization, used it to reach into the Wi-Fi range of a second, and
RDP'd from a dual-homed host on the first network onto the real target's
enterprise Wi-Fi - using previously compromised credentials for that
target. It's lateral movement conducted almost entirely without
traversing the public internet: the RDP session originates from a
device physically (in RF range) or logically adjacent to the victim,
which is a large part of why Volexity gave it a distinct name rather
than filing it as ordinary remote-access abuse.

## The Present Problem
RDP is a legitimate, heavily-used admin tool, so "RDP session observed"
is low-signal by itself. What's missing from a flat lookup is the
*precondition* - this incident shows RDP lateral movement here required
both a working credential (T1078) and prior reconnaissance to even
identify the reachable target network (T1059.001, the PowerShell Wi-Fi
enumeration script). Without modeling those as prerequisites, a
defender has no way to reason about how far upstream a detected RDP
session's actual point of compromise might be.

- Volexity, "The Nearest Neighbor Attack: How A Russian APT Weaponized
  Nearby Wi-Fi Networks for Covert Access" (Nov 2024) - the sole source
  for both edges. Sample_size is honestly 1 for each: this is one
  documented incident, not a pattern observed across multiple reports,
  which is why confidence tops out at 0.8 rather than higher despite the
  mechanism being explicitly narrated.

## What This Enables
"RDP session detected from an unexpected internal or Wi-Fi-adjacent
host, APT28 suspected - what had to be true beforehand?" resolves to two
concrete, checkable prerequisites (a compromised credential, and prior
PowerShell-based network reconnaissance) instead of a generic "check for
lateral movement" prompt.
